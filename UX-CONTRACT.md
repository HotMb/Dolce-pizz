# Dolce Pizz’ behavioral contract
## Scope and authority
User: pickup only, payment on collection, restaurant explicitly confirms orders. Flyers own recipe names/ingredients/prices. Google Maps verified address and phone on 2026-09-22. Hours are provisional pending owner setup. Loyalty defaults to 1 point per paid euro / 100 points for one free-pizza ticket, configurable and disabled until activated by admin. Admin can switch on a per-pizza “2e pizza offerte” offer.

## State and navigation
Real links for routes. Menu local search with clear button, category in URL. Temporary cart only in localStorage, no PII. Orders, wallet and settings in D1. Customer accounts are identified by a French mobile number (06/07) verified with a 6-digit SMS code (Brevo); sessions are HttpOnly cookies stored hashed in D1 (90 days). Codes expire after 10 minutes, allow 5 attempts, one resend per minute, 5 sends per number and 10 per IP per hour. Without an SMS key, loopback previews show the code on screen; production refuses to send. Admin role is explicitly granted using a private, single-use installation code; no first-visitor trust.
## Order lifecycle
pending → confirmed → preparing → ready → completed; admin may also validate straight to preparing (“Valider + envoyer en cuisine”). preparing means the ticket is available in the scoped production screens (`/production`; `/cuisine` redirects), where the Expeditor marks it ready after all stations finish. Tickets print in an 80 mm browser layout. Completion is blocked until the payment/collection workflow exists. Admin may reject pending or cancel any uncompleted order with a reason. Customer may cancel pending only. Optimistic version required; conflict preserves screen and prompts refresh. No reopening or deleting financial history. Retrying creation uses the same idempotency key; all totals recomputed by server in integer cents.

### Production station workflow
Accepted orders enter production under the active restaurant and location. Each physical unit is routed independently: pizzas → Make Line → Oven → Expeditor; prepared foods → Make Line → Expeditor; drinks, desserts and other no-cook items → Expeditor. Quantity is expanded into physical units. The Expeditor sees every unit and cannot mark the order ready until each required station step is complete. Each action carries the expected production revision and requires server confirmation. Unknown legacy routing and unverified allergen data are explicit warnings; they are never presented as a confirmed recipe. Priority is based on promised pickup time and elapsed wait, with channel as context rather than a fixed multiplier that can starve older orders.

### Staff scope and permission workflow
`/equipe` resolves active memberships from the authenticated account, not the legacy admin flag. Server capabilities determine visible sites, stations and read/write controls. A user without memberships sees their own account identifier and an empty-state explanation. Only an organization owner grants/revokes site roles, after a confirmation naming the person/site/role; org-level owner rows are protected. Input stays in memory after errors or site changes, never in URLs or persistent browser storage. Member rows are keyed to their loaded scope, paginated ten at a time with a visible server-limit warning. API requests abort or ignore superseded responses. Capabilities refresh every thirty seconds and on focus/reconnect; offline blocks writes. 401/403 removes tickets and refreshes access, with a sign-in path after session expiry.

### Staff order intake workflow
`/equipe/commande` exposes Comptoir or Centre d’appels only when the active account has that role at an authorized site. The employee confirms the pickup site and server-issued slot; product, modifiers, allergen snapshot and enabled “2e pizza offerte” pricing are checked again on the server. The created order enters `preparing`, with `pickup` and `due_at_pickup`; this screen never captures payment or card data. The call-center postal code is advisory until each branch’s service zones are configured, so the employee must explicitly choose the pickup site. A mobile is stored for ready-notification delivery only when the client explicitly agrees; this does not grant marketing consent. The same UUID request key is reused after an uncertain response; the UI blocks edits until that attempt is resolved. No order PII or draft is written to local storage or the URL.

### Ready notification workflow
Expeditor readiness atomically queues a service event for direct pickup orders with a captured confirmed mobile. A separate server-only consumer checks scope, current readiness, verified contact and a two-hour freshness limit. A provider receipt means accepted, not delivered. Ambiguous provider/network results and expired claims require reconciliation and are never resent automatically. A dry run reports eligibility without modifying the queue or sending; marketing consent is separate. See `docs/notifications.md` for operational configuration.
## Scheduling
Europe/Paris with DST. Slots use UTC identity and French local display. Seven-day horizon, 15-minute intervals, configurable lead and cutoff, daily hours including midnight, exceptions, per-slot order capacity. Server revalidates on order creation. Pending orders reserve capacity. Hours setup gate and pause prevent new orders without altering existing ones.
## Loyalty
Opt-in account ledger. Earn rate and discount snapshot stored per order, on the amount actually paid. Points credited exactly once when the team validates the order (confirmed or preparing) and reversed if it is cancelled later, without pushing the wallet below zero. Each rewardPoints = one ticket: a free Senior pizza (XXL pays the difference), on a pizza outside a “2e pizza offerte” bundle; ticket points reserved atomically on submission and restored on rejection/cancellation. No balance supplied by client. One ticket per order. “2e pizza offerte”: same size, chosen among all pizzas, the cheaper of the two is free; lib/pricing.ts is shared by browser and API.
## Feedback and recovery
No native alerts/confirms. noValidate forms, own validation, persistent inline errors and first-invalid focus. Busy buttons prevent double submit without geometry change. Typed order draft retained if request fails. Polling ignores stale replies and pauses while hidden. No fake success on failed APIs. Updates never silently overwrite dirty settings.

fr-FR, EUR, Europe/Paris. Dialog focus trap, Escape, return focus; French close labels. Labels for every field; associated validation. 44px primary targets. 200% reflow, reduced motion, text contrast, live status, no color-only information. Z-index: header20, cart30, dialog50, toast100.
